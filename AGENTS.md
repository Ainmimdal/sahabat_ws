# Sahabat Robot Contributor Guide

This is a ROS 2 workspace for a physical differential-drive robot. Changes can
affect motors, localization, obstacle detection, and emergency-stop behavior.

## Read first

- Start with `PROJECT_STATUS.md` for the known working hardware and commands.
- Use `OPERATIONAL_RUNBOOK.md` for canonical operational and diagnostic entry
  points.
- Treat the existing working tree as user-owned. Preserve unrelated changes.

## Safety rules

- Never start motors or send nonzero `/cmd_vel` commands during automated
  validation.
- Do not run a launch file against connected hardware merely to test syntax.
  Prefer parsing, building, linting, or `ros2 launch ... --show-args` when its
  hardware-probing side effects are understood.
- `/emergency_stop` is latched. Publish `true` to stop and publish `false` only
  after a person confirms the area is safe.
- Keep exactly one publisher for each TF edge. AMCL owns `map -> odom` during
  localization; the EKF owns `odom -> base_link` when enabled.
- Do not change wheel geometry, motor polarity, velocity limits, controller
  tuning, sensor transforms, or costmap footprints without a physical-robot
  test plan.
- Do not expose the unauthenticated robot API outside a trusted private network.

## Build and validation

Build the robot package incrementally:

```bash
colcon build --packages-select shbat_pkg --symlink-install
source install/setup.bash
```

Keep `build/` and `install/` unless performing an intentional clean rebuild.
They are ignored workspace output and support fast iteration. Old `log/`
content may be cleaned separately when it is no longer diagnostically useful.

Validation should proceed from least to most invasive:

1. Parse or compile changed source files.
2. Run focused unit and lint checks.
3. Build only affected packages.
4. Inspect launch arguments and node wiring without starting motion.
5. Run sensor-only checks where possible.
6. Perform physical motion tests with a person beside the emergency stop.

Repository-wide lint currently reports legacy style debt. Do not combine broad
formatting with operational behavior changes; keep cleanup patches reviewable.

## Launch compatibility

Canonical entry points are:

- `bringup.launch.py` for hardware bringup without Nav2
- `navigation.launch.py` for `odom_only`, `mapping`, or `localization`
- `operations.launch.py` for gallery localization and patrol

Commands documented in `PROJECT_STATUS.md` remain compatibility interfaces.
Do not remove or redirect them until the canonical replacements have passed
equivalent physical-robot smoke tests.

## Files and runtime state

- Do not delete suspected legacy source, launch, configuration, map, or vendor
  files based only on static reference searches.
- Confirm candidates against documented commands, manual tooling, build
  dependencies, and physical smoke tests first.
- Generated bytecode, screenshots, and TF reports are not runtime dependencies,
  but do not remove user artifacts without explicit approval.
- Prefer configurable runtime paths over writing new state into installed
  package directories. Preserve existing waypoint and map data during migration.

## Handoff expectations

State clearly:

- which files and behavior changed;
- which checks passed or failed;
- whether hardware was connected or probed;
- whether any motor movement occurred;
- which physical tests remain required.
